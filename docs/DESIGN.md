# Automaton — дизайн

## Концепция

Оверхол Factorio 2.0 для игры с друзьями. Из игры убрана вся «автоматическая» логистика и добыча:
конвейеры, буры, манипуляторы, логистические роботы, насосы и нефтевышки. Их работу делают
**автоматоны** — наземные (а позже и летающие) машины, которые выполняют программы, написанные
игроками на языке, похожем на TypeScript. Завод строится не из лент и манипуляторов, а из маршрутов и алгоритмов.

## Принятые решения

| Тема | Решение |
|---|---|
| Версия игры | Factorio 2.0 (stable), только `base`, без зависимости от Space Age |
| Аудитория | Мультиплеер с друзьями: детерминизм и отсутствие десинков обязательны. Публикация на портал не цель |
| Убираем | Конвейеры (все виды, подземные, разделители, загрузчики), буры (включая нефтевышку), манипуляторы (все), логистических роботов и логистические сундуки, кроме сундука хранения, прибрежный насос |
| Оставляем | Трубы, помпы, резервуары, поезда, машину/танк, строительных роботов, робопорт, сундук хранения, сборщики, печи, лаборатории, комбинаторы |
| Движение | Наземные машины ездят по земле с поиском пути и сталкиваются со зданиями и друг с другом: проезды и пробки — часть головоломки. Поздние летающие модели летают по прямой без столкновений, как дроны, — для больших масштабов. От столкновений наземных можно отказаться позже, если не окупятся |
| Энергия | Mk1 жжёт топливо, Mk2+ работают от аккумулятора и заряжаются на станциях |
| Графика | Перекрашенные ванильные спрайты |
| Язык программ | Строгое подмножество TypeScript: классы, интерфейсы, наследование, лямбды, функции высшего порядка. Статическая типизация с выводом типов. Без `async`/`await`: действия машины блокирующие |
| Код мода | TypeScript, сборка в Lua через TypeScriptToLua; типы API игры — typed-factorio 3.x (Factorio 2.0) |

## Игровой цикл

- **Старт.** Freeplay; вместо бура и печи в стартовом наборе — два автоматона Mk1 и метки. Библиотека команды
  пустая — программы пишут игроки (решение 2026-10-09); примеры — в руководстве и папке `examples/`.
  Ручная добыча и ручной крафт игрока остаются.
- **Программа.** Игрок ставит автоматон, открывает его окно, выбирает программу из библиотеки команды
  (или пишет новую) и запускает. Программы общие для всей команды (force); изменение программы
  перезапускает все машины, которые её выполняют.
- **Адресация мира.** Метки (сущность с именем) и зоны (прямоугольник, выделенный инструментом
  «Программатор»): в коде `marker("coal-depot")`, `zone("north-iron")`, `find("stone-furnace", zone("smelter"))`.
- **Ошибки.** Ошибки компиляции показываются в редакторе с номером строки. Ошибка выполнения
  останавливает машину, поднимает оповещение и подсвечивает строку.
- **Редактор в игре.** Программа открывается в просмотре с подсветкой; «Править» или клик по строке —
  обычное поле ввода (цвета в нём нет: rich text стал бы частью кода); после публикации — снова просмотр,
  ошибки — красным в своих строках. «Проверить» и переход в просмотр компилируют без публикации (не на каждое
  нажатие клавиши: ввод в сети исполняется у всех игроков). Подробно писать — в VS Code.
- **Прогрессия.** Язык доступен целиком с самого начала (урезанный язык раздражает).
  Исследованиями открываются модели машин (скорость, груз, бак, энергия), ресурсы «процессора»
  (бюджет инструкций, память) и возможности API (жидкости, сигналы цепей, связь между машинами).
- **Угрозы и бой.** Автоматоны — военные цели: кусаки на них нападают, маршруты придётся защищать.
  Для этого есть боевые модели (пулемёт, позже ракеты или огнемёт) с командами `attack`, `guard`, `patrol`;
  сам бой ведёт движок игры.

## Автоматон

- **Сущность.** Прототип типа `unit` на стороне игрока. Движение — `entity.commandable.set_command`
  с `go_to_location` (поиск пути делает движок), завершение — событие `on_ai_command_completed`.
  Ставится из предмета через сущность-заглушку, которая в `on_built_entity` заменяется на юнит
  (проверить в спайке, этап 1).
- **Груз.** Скриптовый инвентарь `game.create_inventory(n)`, отдельный слот топлива,
  бак для жидкости (тип + количество в `storage`).
- **Встроенная библиотека** — в [API.md](API.md): вывод (`print`, `say`, `chat`, `alert`), движение,
  предметы, здания, жидкости, зрение (`scan.*`), карта, связь между машинами (сообщения, общая доска,
  очереди задач), табло (пиксельный холст), бой, сигналы цепей, время и мир.
- **Руки, глаза, радио.** Со зданиями машина работает как персонаж — только в радиусе досягаемости,
  подъезжать надо самой. Состояние зданий и других машин видно только в радиусе зрения. Связь
  (сообщения, доска, задачи, табло) — на любом расстоянии. Отсюда типичная схема: машина находит
  оркестратора, регистрируется у него и получает задания вместе с нужной информацией о мире.
- **Рассылки всем нет** (решение после замеров масштаба): машина публикует обновления (`publish`),
  получают их только подписанные на неё по id (`subscribe(id, тема?)`), подписок сколько угодно.
  Найти машину — по доске или зрением. Рассылка всем подписчикам темы росла как N²: 5000 машин — 121 мс
  на тик (8 UPS); цена публикации теперь — число её подписчиков.
- **Идентификация.** У машины есть `id` и имя, видны над ней; при подборе сохраняются в предмете
  (`item-with-tags`) вместе с памятью машины.
- **Энергия.** Расходуется на пройденный путь и на действия. Кончилась — машина встаёт с оповещением.
- **Статус.** Над машиной рисуется (rendering API) иконка состояния и ошибки.
- **Анимации.** Набор анимаций зашит в тип сущности: у юнита только бег (кадры идут по пройденному
  пути — стоя он застывает) и атака, простоя нет. Работа показывается накладками rendering, которые
  крутятся по времени: при добыче — анимация бура у месторождения (буры из игры убраны, графика
  свободна). Полноценные анимации (задача 1.4): прозрачный спрайт юнита и накладки
  (бег, простой, добыча) по 8 направлениям, переключаемые по состоянию.

## Язык

**Принцип: каждая программа — валидный TypeScript.** Поэтому программы можно писать в VS Code
с файлом `automaton.d.ts` (автодополнение, проверка типов, форматирование) и вставлять в игру.
Обратное не верно: поддерживается подмножество, неподдерживаемое даёт понятную ошибку компиляции.

**Версия 1:**
- `let` / `const`; `number`, `string`, `boolean`, `null`, `undefined`; массивы, объектные литералы,
  шаблонные строки; `++` / `--` и составное присваивание.
- Деструктуризация (`const { a, b } = obj`, `const [x, y] = arr`), `...` в массивах, объектах и параметрах,
  `?.` и `??`.
- Функции, стрелочные функции, замыкания, функции высшего порядка; явные параметры типов в вызовах (`receive<T>()`).
- `if` / `else`, `while`, `for`, `for…of`, `break` / `continue`, `return`, `switch`, тернарный оператор,
  `try` / `catch` / `finally`, `instanceof`.
- Классы: поля, конструктор (в т.ч. `readonly`-параметры), методы, геттеры, `extends` / `super`,
  `abstract`, `implements`, `static`.
- Интерфейсы и псевдонимы типов, `T | null`, литеральные и размеченные объединения.
- `try` / `catch` / `throw`: ошибки действий (нет пути, нет предмета) — исключения.
- Стандартная библиотека: методы массивов (`map`, `filter`, `reduce`, `find`, `some`, `every`, `forEach`,
  `sort`, `slice`, `includes`, `push`, `pop`, …), `Map`, `Set`, `Math`, основные методы строк.

**Не поддерживается:** `async` / `await` / `Promise`, генераторы, декораторы, `any`, `eval`,
регулярные выражения, `Date`, прототипы и переопределение `this`, `==` (только `===`).
`import` / `export` между программами команды — раздел «Модули».

**Типизация.** Проверка типов при сохранении программы: структурная совместимость как в TS,
вывод типов для переменных и лямбд, сужение типов (`=== null`, `instanceof`, проверка поля-дискриминанта).
Делается отдельным этапом после рабочего компилятора; до него ошибки типов ловятся при выполнении,
а статическую проверку даёт VS Code + `automaton.d.ts`.

## Модули (этап 17)

Решения по [вариантам](https://claude.ai/artifact/YUAGvwsHTzxQyUumYKNjmq): 1B, 2A, 3B+3C+3D, 4A.

**Модуль — программа команды.** Имя программы может содержать папки: `Логистика/Перевозчик`,
`lib/Помощники`. Папка существует, пока в ней есть программы (как в git); переместить = переименовать
с другим путём. В окне программ — дерево, в папке VS Code — такие же подпапки.

**Импорт — относительный путь от папки модуля**, как в TypeScript: `import { nearMarker } from "../lib/Помощники"`
(расширение не пишется). Поддерживается: `import { a, b as c }`, `import * as ns`, `import x` (default),
`import type` и `{ type T }`, `import "./x"`; `export` перед объявлением, `export { a, b as c }`,
`export default`, `export { a } from`, `export * from`. Нет: динамического `import()`, `export =`, `require`.

**Исполнение как у ES-модулей.** Модуль выполняется один раз у каждой машины до того, кто его
импортирует, в порядке зависимостей. Переменные модуля — свои у каждой машины. Импортированные имена
живые и только для чтения. Циклический импорт — ошибка публикации.

**Библиотека — по содержимому (2A):** на верхнем уровне только объявления (`import`, `export`,
`function`, `class`, `interface`, `type`, `const`/`let`). Есть вызов, цикл, `if`, присваивание — это
программа. Библиотеку нельзя назначить машине; в окне программ она помечена.

**Публикация = сборка.** Программа компилируется вместе со всеми модулями, которые импортирует
(их опубликованными версиями), в один Lua-чанк; запись программы хранит, от каких модулей зависит.
Новая версия библиотеки пересобирает всех, кто от неё зависит (и дальше по цепочке): собралась —
новая версия, машины перезапускаются; не собралась — остаётся прежняя сборка и предупреждение
«не собирается с новой версией …» в окне программ.

**Удаление и переименование (4A).** Используемую библиотеку удалить нельзя: окно показывает, кто
её импортирует. Переименование или перенос в другую папку сам правит `import` в зависимых программах
и публикует их новые версии.

**Ошибки и строки** — с именем модуля: `lib/Помощники:12:5`. В сгенерированном Lua номер строки
кодирует модуль: `модуль × 1 000 000 + строка` (таблица строк, точки остановки и трассировки не меняются).

**Обмен программами строкой (18.3: A1, B1, C2).** Экспорт — окно с деревом программ и галочками (открытая
программа отмечена; модули, без которых отмеченное не соберётся, отмечаются сами и не снимаются), строка
`am1:` + `helpers.encode_string(JSON)` выделена для Ctrl+C. Импорт — вставленная строка разбирается сразу:
новая / та же (пропускается) / есть с другим текстом — выбор у каждой: заменить, рядом «(2)», пропустить;
публикация — проходами (модуль раньше программы, которая его импортирует), с правами публикации. Кнопки — в нижнем
ряду окна программ, рядом с VS Code.

**Описания API на двух языках (18.4).** Источник — объявления в `docs/API.md`: у описания английская строка
`@en` рядом с русской. Генератор пишет `automaton.d.ts` (русский; его же читает проверка типов в игре) и
`automaton.en.d.ts`; папка VS Code и окно «Типы для VS Code» — на языке игрока. Непереведённое описание
роняет `npm test`.

**Справка в игре (18.5: A2, B1, C1, D1, E1).** Ярлык «?» на панели быстрого доступа и F1. Окно в две колонки:
поиск и список (начало — «Первые шаги» и «Частые ошибки»; разделы `docs/API.md` с объявлениями; при поиске —
по степени совпадения), справа — объявление в цвете, описание и пример раздела (у разделов без примера в API.md
они дописаны). «Выделить пример» — текст выделен для Ctrl+C. Данные собирает генератор из `docs/API.md` на двух языках.

**Все машины (18.6: A1, B1, C1, D1).** Ярлык на панели и «Машины: N» у программы в окне программ (с фильтром
по ней). Таблица: машина, программа, состояние (ошибка — красным, нет топлива и застряла — оранжевым, стоит —
серым), топливо; сортировка по столбцу, страницы по 50, обновление раз в секунду. Фильтры с числами по всему
парку: с ошибкой, без топлива (меньше 2% или состояние «нет топлива»), стоят (нет программы, завершена, пауза).
Клик — удалённый вид (камера следует за машиной) и окно машины.

**Чертежи с машинами (18.7).** Машина — юнит, игра её в чертёж не кладёт: при создании чертежа и Ctrl+C машины
в рамке добавляются размещателями своей модели с тегом — имя программы команды и параметры (JSON). Построенный
размещатель (рукой, строительным роботом, скриптом) — машина с новым именем, программа назначается и запускается
сразу; программы с таким именем нет — машина без программы и сообщение команде. Тексты программ чертёж не несёт —
для этого строка обмена (18.3). Рамка над одними машинами чертежа не даёт: игра не создаёт чертёж без зданий,
и события нет (ограничение игры, проверено `npm run test:sim`).

**Отладка (18.8: A1, B1, C1).** Точки остановки — у машины, в окне «Отладка» (из окна машины). Компилятор ставит
перед каждой инструкцией возобновляемой функции проверку `BPON and QS == 0 and BRK(строка)`; пауза — как у кванта
(кадр сохраняется, продолжение — с метки после проверки), кадр с переменными — один блок BRKSAVE на функцию, у тел
try — обычная короткая пауза. Без отладки — одна проверка upvalue на инструкцию: худший случай (тесный цикл из одной
инструкции) +28%, обычно 3–14%, 300 машин в игре — +0.18 мс к тику. «Шаг» — до следующей строки (через тот же
механизм). Переменные — верхнего уровня программы и модулей (компилятор отдаёт их места в кадре главной функции),
me.memory, параметры. Короткие функции (без пауз) остановок не имеют; программы, собранные раньше, — «Пересобрать».

**Выбор программы у машины (3B+3C+3D):** окно выбора с поиском, папками, числом машин на программе
и недавними; Shift+ПКМ / Shift+ЛКМ по машине — скопировать и вставить программу с параметрами;
режим «Программатора» — выделить машины рамкой и запустить на всех одну программу, рамка с Shift — остановить.

## Архитектура исполнения

Программы компилируются из TypeScript в Lua один раз — при публикации — и дальше исполняются
как обычный Lua.

```
Игрок жмёт «Опубликовать» в редакторе
  → исходник попадает в игру как обычное действие игрока (так Factorio синхронизирует любой ввод)
  → у всех участников одинаково: разбор → проверка типов → проверка безопасности → генерация Lua → load() в песочнице
  → ошибка: программа отклонена, автор видит ошибки со строками
  → успех: новая версия в библиотеке команды; все машины с этой программой выполняют одну функцию
В сейве: исходник + сгенерированный Lua. При загрузке сейва — только load(), без компилятора.
```

**Почему компиляция в Lua, а не интерпретатор.** Замер в Lua самой Factorio 2.0.77 на одной и той же
нагрузке (100 тыс. итераций цикла):

| Способ | Время | Относительно Lua |
|---|---|---|
| Обычный Lua | 2.1 мс | 1× |
| Сгенерированный Lua со счётчиком инструкций | 3.0 мс | 1.4× |
| То же, лямбды как сохраняемые данные | 5.5 мс | 2.6× |
| Возобновляемая функция: переменные всегда в таблице-кадре | 7.4 мс | 3.5× |
| **Возобновляемая функция: `goto`, переменные в кадр только при паузе** | **2.9 мс** | **1.3×** |
| Интерпретатор байткода на Lua | 83.5 мс | 39× |

`load()` компилирует 500 строк сгенерированного Lua за 0.2 мс. Пауза и продолжение возобновляемой
функции стоят ~0.14 мкс; с паузами каждые 50, 500 и 5000 итераций результат одинаковый.

**Замер настоящего компилятора** (3.11, `npm run bench:game` — Lua Factorio 2.0.77; нагрузки в
`src/test/langBench.ts`, время относительно того же алгоритма на обычном Lua):

| Нагрузка | Без пауз | Пауза каждые 50 витков |
|---|---|---|
| Короткие функции (расстояния между точками) | 1.36× | 1.58× |
| Циклы по массиву объектов (тот же, что у прототипа) | 1.99× | 2.73× |
| Методы класса (`this.n += x`) | 4.0× | 4.45× |
| Лямбды `filter` / `map` / `reduce` | 3.5× | 3.55× |

Разница с прототипом (1.3×) — семантика JS и безопасность: длина массива читается на каждом витке,
индексы с 0 (`a[i + 1]`), у чтения поля — проверка на геттер/метод, у `+` — проверка, не строка ли.
Что сделано: вывод «всегда число» для переменных и функций (тогда `+` — сложение Lua), вывод
«всегда массив / объект / экземпляр класса» (прямой доступ к полям и методам), быстрые пути чтения
полей и индексов без вызова функции, счётчики кванта в upvalue, `Math.*` от чисел — напрямую.
Методы и лямбды упираются в неизвестные типы: их ускорит проверка типов (этап 12).

**Где компилируется.** Factorio — детерминированный lockstep: каждый участник сам исполняет всю игру
и весь Lua модов, поэтому «выполнить только на сервере» или «только у клиента» нельзя. От игрока
в игру попадает только исходный текст, и каждый участник компилирует его одинаково, один раз при
публикации. Готовый Lua от клиента не принимается никогда: модифицированный клиент прислал бы
что угодно, а наш компилятор — единственные ворота. Бинарный байткод Factorio загружать не даёт
(проверено), и он не нужен: после `load()` программа уже лежит в памяти как байткод Lua.

**Бесконечные циклы — норма, но не захватывают время.** `while (true)` — обычный главный цикл машины.
У каждой машины есть квант инструкций на тик (зависит от модели). Исчерпала — программа ставится на
паузу на ближайшем витке цикла или входе в функцию и со следующего тика продолжается с того же места.
Это не ошибка и не блокировка: остальные машины и игра получают своё время. Ожидание через
`wait` / `receive` / действия экономит квант и энергию, поэтому писать так выгоднее, но не обязательно.

**Возобновляемые функции.** Корутин нет, а функции нельзя хранить в `storage`. Поэтому компилятор по
графу вызовов делит функции на два вида:
- **короткие** — без циклов, без рекурсии, без действий и вызывают только такие же: обычная функция Lua,
  полная скорость (так компилируется большинство лямбд вроде `f => f.count(ore) < 10`);
- **возобновляемые** — все остальные. Тело разворачивается в плоский код на `goto` (Lua 5.2), все
  переменные — обычные локальные переменные Lua; точки остановки — на витках циклов, входах в функции
  и вызовах действий. Только при паузе переменные и номер точки складываются в таблицу-кадр (простые
  данные в `storage`), при продолжении — восстанавливаются, и `goto` прыгает в нужное место. Пауза во
  вложенном вызове поднимается по цепочке кадров. Так TypeScript переводит генераторы в старый JavaScript.
- Замыкания, которые переживают паузу, хранятся как данные `{функция, захваченные переменные}`.
  Методы массивов высшего порядка (`map`, `filter`, `forEach`) есть в двух версиях — обычной и
  возобновляемой, — компилятор выбирает по лямбде.
- В Lua 5.2 не больше 200 локальных переменных на функцию: если не помещаются, лишние уходят в кадр.

**Безопасность: чужая программа не может сломать игру.**
1. **Публикация — это проверка, а не запуск.** Разбор, типы, белый список конструкций языка и API.
   Не прошла — не публикуется.
2. **Песочница.** `load(текст, имя, "t", окружение)`: программа не видит `game`, `storage`, `_G`, `load`,
   `require` (проверено).
3. **Никаких прямых обращений к значениям Lua.** Методы строк и массивов — только через нашу
   библиотеку. Причина: даже в песочнице у строк работают методы Lua, и `('x'):rep(1e9)` съест память
   у всех (проверено). Поля читаются напрямую (`o.x`, `nil` — медленный путь рантайма), кроме имён
   функций библиотеки `string` (`rep`, `sub`, …). Это безопасно, потому что **объекты игры попадают в
   программы только обёртками-таблицами**, а не userdata (у `LuaEntity` прямое `e.surface` дало бы
   доступ к поверхности) — обязательное правило для API (этап 4).
4. **Квант и лимиты.** Квант инструкций на тик: бесконечный цикл ставится на паузу, а не валит игру
   (проверено). Жёсткие лимиты, которые дают ошибку: глубина вызовов, число объектов, длина строк,
   размер сообщений, примитивы табло.
5. **Изоляция.** Каждая машина исполняется под `pcall`: ошибка программы — ошибка этой машины, не мода.
6. **Карантин.** Программа, которая раз за разом упирается в лимиты, автоматически приостанавливается,
   автору и админам — оповещение.
7. **Права и квоты.** Настройка карты «кто может публиковать программы» (все / админы / список);
   лимиты на размер программы и частоту публикаций на игрока; квоты команды на машины, доску,
   очереди и табло.

**Кэширование и пакетная обработка.**
- Одна программа — одна скомпилированная функция на все машины; у машины только свой кадр.
- Неизменное (рецепты, предметы, стопки) кэшируется навсегда; `find` по зоне — до постройки или сноса
  в этой зоне; одинаковые `scan` из одной точки в одном тике — один запрос к движку.
- Машины с одной программой исполняются подряд, бюджет на тик раздаётся пачками.
- Действия завершаются через «колесо таймеров»: каждый тик обрабатываются только машины, у которых
  что-то закончилось, а не все.
- Сообщения доставляются пачкой в начале тика; табло перерисовываются раз в кадр, только изменения.
- Тяжёлое делает движок: поиск пути, движение и бой юнитов, поиск сущностей, перенос предметов,
  рисование. Колонна машин с одним маршрутом — одна группа юнитов и одна команда.

**Модель времени — решено оставить (после этапа 17).** Квант на витки циклов и входы в долгие функции,
ожидание бесплатно, тяжёлые вызовы библиотеки выполняются целиком и дают долг. Рассмотрены и отклонены:
«поштучно без долга» (паузы внутри вызовов), «шаг до ожидания — за один тик» (как `await` в JS / Screeps:
предсказуемо, но долгий расчёт пришлось бы дробить `wait(0)`), «фиксированная цена вызова» (нужны
жёсткие пределы размеров) — [сравнение на одном примере](https://claude.ai/artifact/8LWrfrhxsGcbbjMw2kmgBT).
Правила и цены для игроков — API.md, «Время программы»; руководство — «Время: квант, ожидание, долг».

**Планировщик.** Общий бюджет инструкций на тик (настройка карты) делится между готовыми к работе
машинами по кругу; у каждой — квант по её модели. Машина, израсходовавшая квант, встаёт в конец
очереди. Ждущие машины бюджет не тратят. При перегрузке игра не тормозит — машины «думают» медленнее,
и ни одна не может отнять время у остальных.

**Системные вызовы.** Блокирующий вызов — такая же точка остановки: функция сохраняет кадр, действие
уходит в систему действий; по завершении результат кладётся в кадр, и функция продолжается с этого места.

**Чистые модули.** Лексер, парсер, проверка типов, проверка безопасности, генератор кода и рантайм-
библиотека не используют API Factorio и тестируются вне игры.

**Структура кода.** Мод пишется на TypeScript; TypeScriptToLua собирает его в Lua в папку `mod/`,
которая и подключена к игре.

```
src/                исходники мода на TypeScript
  control.ts, data.ts, data-final-fixes.ts, settings.ts
  lang/             lexer, parser, checker, safety, codegen, runtime (библиотека для сгенерированного кода)
  automaton/        сущность, действия, энергия, груз, планировщик, колесо таймеров
  world/            метки, зоны, кэши
  gui/              редактор, статус, библиотека программ
  prototypes/       автоматоны, предметы, рецепты, технологии, удаление ванили
mod/                папка мода для игры: info.json, changelog.txt, locale/, graphics/ + собранный Lua
tests/              тесты чистых модулей (вне игры), атаки на песочницу, интеграционные (в игре)
tools/              раннер тестов, генератор automaton.d.ts, бенчмарки
```

## Мультиплеер

- Всё игровое состояние — в `storage`, меняется только в обработчиках событий.
- Никаких данных, которые различаются у клиентов: `math.random` → `game.create_random_generator`,
  без `os` / времени; GUI отдельный у каждого игрока, правки применяются в `on_gui_*` событиях.
- В `storage` — только простые данные, без функций и метатаблиц.
- `on_load` не трогает `storage`; он только собирает кэш скомпилированных функций из сохранённого
  Lua-текста (одинаково у всех).
- Скорость игры определяет самый медленный компьютер в компании: бюджет инструкций выбирается с запасом.
- Проверка: `/toggle-heavy-mode` (ловит десинки), локальный сервер + клиент.

## Масштаб

Замеры в Factorio 2.0.77 (`tools/bench/`), добавка ко времени тика пустой карты (~0.36 мс; весь тик — 16.7 мс):

| Сценарий | Время тика | Что происходит |
|---|---|---|
| 100 000 перевозчиков, движение рассчитывается | +0.2 мс | 128 событий за тик, ~1.5 мкс на событие с вызовами API; память Lua 76 МБ, сейв 2.2 МБ |
| 1 000 юнитов с поиском пути | +0.7 мс | 1.6 поездки на юнита за 30 с |
| 5 000 юнитов | +1.9 мс | 0.8 поездки: поиск пути движка не успевает |
| 20 000 юнитов | +4.7 мс, пики 15.6 мс | 0.35 поездки: ~215 маршрутов в секунду на всех |

Выводы:
- **Логика программ масштабируется до 100 000 машин**: колесо таймеров + компиляция в Lua.
- **Наземные машины — физические юниты**, их потолок — несколько тысяч на карту (поиск пути и
  столкновения считает движок). Помогают: очередь запросов пути с бюджетом на тик, повторное
  использование маршрутов (короткие участки по кэшированному пути дешевле длинного поиска),
  обнаружение пробок и застреваний.
- **Летающие машины — подход дронов**: по прямой, без столкновений, движение рассчитывается
  (время = расстояние / скорость), машина «просыпается» только по прибытии. Рядом с игроками они
  видимы и кликабельны, вдали — только данные. Это путь к десяткам тысяч машин.
- Если наземных станет тесно, запасной вариант — расчётное движение и для них вдали от игроков
  (ценой столкновений там, где никто не смотрит).

**Кэш маршрутов** (задача 1.6, `tools/bench/units/run.sh N [random|shuttle|waypoints] [true|false]`).
Челноки ездят между постоянными точками (~300 клеток), как перевозчики:

| 1000 юнитов, 30 с игры | Тик | Доехали |
|---|---|---|
| Без кэша | 1.01 мс | 712 |
| Кэш путей движка (`pathfind_flags.cache`) | 0.86 мс | 657 |
| Свой кэш: путь маршрута ищется один раз, юниты едут перегонами по 20 клеток | 0.85 мс | 697 |

Кэш движка снижает стоимость на ~15%, свой кэш сверху ничего не добавляет — его не строим; поездки
отдаются движку с `cache: true`. На 5000 челноков упор не в поиск пути, а в давку у конечных точек.

## Производительность (этап 13)

Замеры на MacBook разработчика, Factorio без окна, прирост времени тика к пустой карте:

| Нагрузка | Прирост | Команда |
|---|---|---|
| 300 рабочих Mk1 по программе «толпы» (поездки, добыча, рассылка всем, доска, 100 `Math.random` за круг) — до отказа от рассылки | +0.64 мс | `npm run bench:machines` |
| 10 000 рабочих по программе «толпы» без рации | 5.7 мс (60 FPS / 60 UPS с окном) | `npm run bench:scale -- --no-radio` |
| 10 000 рабочих по «толпе», каждая подписана на соседа и публикует ему | 5.4 мс (60 FPS / 60 UPS с окном) | `npm run bench:scale` |
| 100 000 летающих перевозчиков, ~120 посадок за тик, без игроков рядом | +0.95 мс | `npm run bench:flyers` |

Из 0.64 мс у 300 машин: исполнение программ — ~0.26 мс, доставка писем — ~0.13 мс (рассылка всем на 300
подписчиков — худший случай), движение, анимации, действия — по ~0.02–0.05 мс. Профиль по обработчикам
тика пишет `bench:machines` (`BENCHPROF` в логе). Кэши (13.3): `find` по зоне — до постройки или сноса в ней,
одинаковые `scan` в одном тике — один запрос к движку; данные `publish` копируются при чтении.

## Жидкости и баланс воды (этап 7)

Прибрежного насоса и нефтевышки нет: воду и нефть возят машины в баке (`pump`, `fill`, `drain`).

| Параметр | Значение | Ориентир |
|---|---|---|
| Бак Mk1 | 1000 | бочка — 50, резервуар — 25 000 |
| Набор воды, перелив | 500 ед/с | прибрежный насос — 1200 ед/с |
| Нефть | 10 × выработка в секунду | как нефтевышка (скорость добычи 1), выработка падает так же |
| Уран | 1 серной кислоты на руду | как у бура |
| Насос машины | 50 кВт | |

Котёл ест 60 воды в секунду, а вмещает 200 — поэтому машина заливает в резервуар у котлов, а не в котёл.
Цикл водовоза: набрать 1000 (2 с) + залить (2 с) + путь туда и обратно (2D / 6 клеток в секунду):

| Путь до воды D | Цикл | Воды в секунду | Котлов на машину |
|---|---|---|---|
| 15 клеток | 9 с | 111 | 1.8 |
| 30 клеток | 14 с | 71 | 1.2 |
| 60 клеток | 24 с | 42 | 0.7 |

Правило для игроков: **один водовоз на котёл** (две паровые машины, 1.8 МВт) при котельной у воды.
Нефтезавод (базовая переработка) ест 100 нефти в секунду; месторождение со 100% выработки даёт машине
10 в секунду — нужны несколько машин на нескольких месторождениях, как и нефтевышек в обычной игре.
Mk2/Mk3 (этап 8) увеличат бак и скорость.

## Риски

| Риск | Что делаем |
|---|---|
| Компилятор возобновляемых функций сложный | Тесты сериализации (остановить в случайной точке, скопировать кадр, продолжить) и сравнение с эталонным исполнением |
| Лазейки из песочницы | Белый список, всё через рантайм-библиотеку, набор тестов-атак (выход из песочницы, бомбы памяти, циклы, рекурсия) |
| Поиск пути и пробки при тысячах наземных машин | Замерено (раздел «Масштаб»): очередь запросов пути, кэш маршрутов, обнаружение пробок; для больших масштабов — летающие модели |
| Вода для котлов: 60 ед/с на котёл, всё возить машинами тяжело | Баланс баков и скоростей, расчёт на этапе жидкостей |
| Редактировать код в окне Factorio неудобно | VS Code + `automaton.d.ts`, импорт/экспорт через буфер обмена |
| Проверка типов TS разрастается | Жёсткий список поддерживаемого, остальное — понятная ошибка |
| `unit` всегда военная цель | Принимаем как геймплей (защита маршрутов) |
