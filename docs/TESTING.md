# Проверки

| Команда | Что проверяет | Где выполняется | Время |
|---|---|---|---|
| `npm test [фильтр]` | Чистые модули: компилятор, рантайм, всё без API игры | Lua 5.2 вне игры | секунды |
| `npm run test:game` | Код мода на настоящем API игры | Factorio без окна, 5 тиков | ~5 с |
| `npm run shot` | Внешний вид: снимки сцены с машинами | Factorio **с окном**, ~20 с | ~20 с |
| `npm run test:desync` | Сохранение и загрузка посреди работы не меняют ход игры | Factorio без окна, два прогона по 600 тиков | ~4 с |
| `npm run test:desync:heavy` | То же, но сохранение и загрузка каждые 50 тиков (замена heavy mode) | Factorio без окна, 12 перезапусков | ~12 с |
| `npm run test:mp` | Настоящий мультиплеер: клиент подключается к серверу посреди работы 50 машин | Выделенный сервер + клиент **с окном** | ~70 с |
| `npm run bench:machines [N]` | Стресс-тест: N машин (300) по программам, прирост тика и профиль по обработчикам | Factorio без окна | ~15 с |
| `npm run bench:flyers [N]` | 100 000 летающих перевозчиков | Factorio без окна | ~20 с |
| Heavy mode (вручную) | Расхождения на каждом тике | Factorio с окном | минуты |

Все прогоны без окна используют свою временную папку данных и модов, поэтому не мешают открытой игре.

## Тесты вне игры — `npm test`

Файлы `tests/**/*.test.ts`, библиотека `describe` / `test` / `expect` из `src/test/testing.ts`.
TypeScriptToLua собирает их в `build/`, они выполняются в Lua 5.2 (собирается `tools/lua/build.sh` при
первом запуске). Окружение как в Factorio: нет `coroutine`, `io`, `os`, `loadfile`, `dofile`.
Фильтр — подстрока пути: `npm test -- lexer`.

## Тесты в игре — `npm run test:game`

Файлы `src/test/*.test.ts`; каждый новый файл добавляется импортом в `src/test/index.ts`. Тесты
выполняются на первом тике новой карты (без врагов, сид 1) и могут ставить здания, создавать
сущности и вызывать любые функции мода. Включаются только служебным модом `automaton-test`,
который создаёт скрипт; в обычной игре и в zip мода их нет.

Тесты идут по очереди. Если нужно дождаться игровых событий (машина едет, печь плавит), тест
продолжается позже: `t.after(тики, () => { …проверки… })`. Все тесты обязаны закончиться к тику 12000 (`DEADLINE_TICK` в `src/test/runner.ts`),
иначе тест считается упавшим («не закончился к тику …»).

Правила, чтобы тесты были стабильными:
- **Не опираться на рельеф карты.** Генерация карты при `--create` многопоточная: какие клетки и деревья
  «первые попавшиеся», меняется от прогона к прогону. Нужную местность тест создаёт сам
  (`set_tiles`, `find_non_colliding_position`).
- **Убирать за собой** созданные сущности: тесты идут на одной карте друг за другом.

## Сохранение посреди работы — `npm run test:desync`

- **Прогон A:** 600 тиков подряд.
- **Прогон B:** 300 тиков → сохранение → загрузка → ещё 300.
- На тике 600 в обоих прогонах мод пишет полный снимок `storage` (`src/test/stateDump.ts`).
  Снимки должны совпасть, иначе выводится разница.

Ловит состояние, которое живёт вне `storage` (переменные модулей, кэши, от которых зависит ход игры),
и изменения `storage` в `on_load`. Проверено на подложенной ошибке: счётчик в переменной модуля дал
`601` без сохранения и `301` с сохранением.

Снимок — `storage`, объекты игры в нём заменяются стабильным описанием (имя, номер, позиция): serpent
печатает их с адресами памяти, разными в разных прогонах. `DESYNC_SHOW=1 npm run test:desync` печатает снимок.

Сценарий на карте (`src/test/stateDump.ts`): машины ставятся, одна гибнет, одну подбирают; после
сохранения подобранную ставят обратно из предмета и ставят новую. Состояние сценария нигде не хранится —
всё ищется на карте, иначе сам сценарий сломался бы при загрузке. Сценарий растёт вместе с модом:
дальше в нём появятся машины, работающие по программам.

## Тяжёлый прогон — `npm run test:desync:heavy`

Как `test:desync`, но в прогоне B игра сохраняется и загружается на тиках 50, 100, …, 550 (11 раз).
Сценарий — 50 машин: 40 машин «толпы» (поездки по кругу, добыча, сообщения, доска, `Math.random`)
и машины по одной на каждую возможность (шахтёр, жидкости, связь, патруль). Heavy mode игры без окна
не включить — этот прогон ловит то же самое на 11 точках.

## Мультиплеер — `npm run test:mp`

Выделенный сервер (`--start-server`) на карте сценария desync и клиент с окном (`--mp-connect`),
который подключается посреди работы — то есть загружает карту, как друг, зашедший в идущую игру.
Клиент играет 45 секунд; провал — «Multiplayer desynchronisation» или ошибка скрипта в логах сервера
или клиента. Проверено на подложенной ошибке (счётчик в переменной модуля решал, ставить ли сундук):
тест поймал десинк через 2 секунды после подключения.

## Heavy mode — вручную

Heavy mode каждый тик сохраняет и загружает игру и сравнивает состояние, поэтому ловит расхождения,
которые `test:desync` может пропустить (между тиками 300 и 600 ничего не сломалось, а в другой момент —
сломалось). Работает только в одиночной игре с окном. Перед плейтестом и после больших изменений
логики машин:

1. Запустить игру (F5 или Steam) и загрузить карту, где машины работают по программам.
2. В консоли игры (`/`) ввести `/toggle-heavy-mode`. Игра заметно замедлится.
3. Дать поработать 1–2 минуты: поставить и подобрать машины, сменить и опубликовать программу,
   сохранить и загрузить игру.
4. `/toggle-heavy-mode` ещё раз — выключить.

При расхождении игра сообщает о десинке и сохраняет отчёт в папку данных
(`~/Library/Application Support/factorio/`). В отчёте два состояния — до и после загрузки; разница
указывает на данные, которые не попадают в сохранение.

## Частые причины десинков

1. **Состояние вне `storage`.** Переменные модулей и кэши допустимы, только если они заново и одинаково
   собираются из `storage` в `on_load` (например, скомпилированные программы машин).
2. **Изменение `storage` в `on_load`.** Нельзя: `on_load` есть только у загрузившегося игрока.
3. **Данные конкретного клиента в логике игры.** Разрешение экрана, язык, настройки графики,
   состояние GUI — только для интерфейса, не для решений, влияющих на мир.
4. **Случайность и время.** `os` в Factorio нет; случайные числа — `game.create_random_generator` с сидом
   из состояния игры.
5. **Подписка на события по условию.** Если обработчик регистрируется в зависимости от состояния, то
   в `on_load` он должен регистрироваться так же, иначе у загрузившегося игрока события пойдут иначе.
6. **Метатаблицы в `storage`.** Не хранить; если всё же нужно — `script.register_metatable`.

## Снимки экрана — `npm run shot`

Сцена `src/test/visual.ts` (машины в каждом занятии и направлении, бегущие машины, здание, персонаж для
сравнения) снимается через `game.take_screenshot`; снимки — в `build/visual/`. Игра запускается с окном
(на секунды), с переменной `SteamAppId=427520`, иначе Steam-версия перезапускает себя через Steam.
Нужен для проверки внешнего вида без человека; на этапе 5 — и для интерфейса.
